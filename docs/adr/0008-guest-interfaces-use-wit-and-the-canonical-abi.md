# 8. Guest interfaces are described in WIT and use the canonical ABI

Date: 2026-08-13

## Status

Accepted

## Context

Record 0007 established that guests are core modules, because the runtime cannot
load components, and left one question open: whether the ABI those modules speak
should be one we design, or the canonical ABI that the component model tooling
already emits.

The stake is the SDK. Our own ABI means writing and maintaining a binding
library for every guest language we support, and updating all of them every time
the interface changes. The canonical ABI means writing an interface once in WIT
and letting `wit-bindgen` produce the guest side for Rust, Go and Python, at the
cost of the host implementing the lifting and lowering rules itself.

The cost of that implementation was the unknown, so it was measured rather than
estimated. A guest was written in Rust against a WIT world exporting
`greet(string) -> string` and `checksum(list<u8>) -> u32`, compiled to a core
module with `cargo` alone, and called from Java.

What the toolchain produced was exactly what a host needs:

```
(export "memory")
(export "greet")            takes offset and length, returns an offset
(export "cabi_post_greet")  releases what the return allocated
(export "checksum")         takes offset and length, returns a number
(export "cabi_realloc")     the guest's allocator
```

Reading a string argument in, calling the function, reading the pair of numbers
it points at, and calling the post return function came to roughly twenty lines
of host code. Lists of bytes cost nothing beyond that, since a string is a list
of bytes with a UTF-8 rule attached.

That is the whole subset we need for a first ABI. It is far cheaper than
maintaining three binding libraries.

The parts of the canonical ABI that are genuinely expensive, being variants,
resources, nested records and the async additions in later versions, are not in
that subset and are not needed to load a plugin, register an event handler and
pass it a payload.

## Decision

Guest interfaces are described in WIT. Guests generate their bindings with
`wit-bindgen`, and the host implements the canonical ABI for the subset those
interfaces use.

The supported subset is numbers, strings and lists of bytes. Anything richer is
expressed by encoding it into a byte list until there is a reason to widen the
subset, and widening it is a decision that gets recorded.

The host calls the post return function after any call that returns a string or
a list, in a finally block, because skipping it leaks guest memory.

Everything a guest returns is untrusted. Offsets and lengths are checked against
the current size of guest memory before any read, and bytes claimed to be a
string are decoded strictly rather than replaced with substitution characters.
A module that breaks the contract is stopped, not accommodated.

We still do not consume components. The component wrapper is discarded, and the
core module inside it is what we load.

## Consequences

One interface definition produces guest bindings for every language the tooling
supports, which is the entire reason the polyglot claim is affordable. Go and
Python stop being three times the work and become a matter of running a
different generator.

Guest authors need only their own language's toolchain. The Rust fixture in this
repository builds with `cargo` alone, because the bindings are generated by a
macro at compile time rather than by a separate command.

We are implementing a specification we do not control. It can change, and our
support for it is a subset that people will assume is complete. The subset has
to be documented as a subset, prominently, or the first person to use a variant
in a WIT file will file a confusing bug.

Restricting ourselves to numbers, strings and byte lists is a real limit on how
expressive the first ABI can be. Encoding structured data into byte lists moves
work to the guest and costs a serialisation format decision later. That is
accepted for now because the alternative is implementing variant and resource
lifting before anything can be loaded at all.

The post return contract is easy to get wrong in a way that does not fail
loudly. It leaks guest memory slowly, and the module that suffers is the guest
rather than the host, so it will be reported as somebody else's bug. Every path
that returns a string or a list has to release it.

Sticking to what the toolchain emits means we can accept components later by
unwrapping them, without changing the ABI or breaking modules written against
what we shipped first.
